# 작업 흐름 계약

이 문서는 AI 작업자가 요청을 처리할 때 따라야 하는 최소 작업 흐름을 정의한다.

## Before Editing

작은 변경이라도 수정 전에 다음을 정리한다.

- 변경 목표.
- 변경 범위.
- 수정할 파일.
- 새로 만들 파일.
- 검증 명령.
- 관련 하네스 문서 갱신 필요 여부.

## Feature Work Flow

1. `09-devlog-mvp-spec.md`에서 해당 기능의 MVP 범위와 구현 단계를 확인한다.
2. `04-feature-spec-template.md`를 기준으로 기능 스펙을 작성하거나 사용자 요청에서 같은 정보를 확인한다.
3. `05-implementation-plan-template.md`를 기준으로 구현 계획을 작성한다.
4. `02-file-structure-contract.md` 안에서 해결 가능한지 확인한다.
5. 실패해야 하는 테스트를 먼저 정한다.
6. RED: 테스트를 먼저 추가하고, 기대한 이유로 실패하는지 확인한다.
7. GREEN: 실패 테스트를 통과시키는 최소 구현만 수행한다.
8. REFACTOR: 테스트가 통과한 뒤 필요한 정리만 수행한다.
9. 계획된 파일만 수정한다.
10. `06-verification-checklist.md`로 완료 여부를 확인한다.

## MVP Phase Order

기본 구현 순서는 `09-devlog-mvp-spec.md`의 `Implementation Phases`를 따른다. 사용자가 명시적으로 순서를 바꾸지 않는 한 이후 단계 기능을 먼저 만들지 않는다.

## Bug Fix Flow

1. 증상과 재현 조건을 정리한다.
2. 버그를 재현하는 실패 테스트를 먼저 작성한다.
3. 실패 테스트가 기대한 이유로 실패하는지 확인한다.
4. 원인을 확인하기 전에는 추측성 수정으로 넘어가지 않는다.
5. 최소 범위로 수정해 실패 테스트를 통과시킨다.
6. 재현 시나리오와 전체 빌드를 검증한다.
7. 실패 원인과 수정 내용을 `08-failure-fix-log.md`에 기록한다.

## TDD Rules

- 코드 변경은 테스트가 먼저다.
- 새 기능은 성공 기준마다 최소 하나의 실패 테스트를 둔다.
- 버그 수정은 재현 테스트가 기대한 이유로 실패하는 것을 확인한 뒤 수정한다.
- 테스트가 즉시 통과하면 기존 동작을 검증한 것이므로 테스트 의도를 다시 확인한다.
- 테스트를 추가하기 어려운 변경은 구현 전에 이유와 대체 검증 방법을 계획에 적는다.
- 리팩터링은 테스트가 통과한 뒤에만 수행한다.

## Failure Fix Recording

- 예상하지 못한 테스트 실패, 빌드 실패, 검증 실패를 수정했다면 `08-failure-fix-log.md`에 기록한다.
- 기록에는 날짜, 실패 증상, 원인, 수정 내용, 재발 방지 테스트 또는 검증 명령을 포함한다.
- TDD의 의도된 RED 실패는 매번 기록하지 않는다. 단, RED 단계에서 실제 버그나 잘못된 설계가 드러나 수정했다면 기록한다.
- 동일한 실패가 반복되면 새 항목으로 추가하고 이전 항목을 참조한다.

## Documentation-Only Flow

1. 문서의 독자와 목적을 확인한다.
2. 기존 문서 구조와 링크를 확인한다.
3. 새 문서가 하네스 흐름에서 어디에 연결되는지 명확히 한다.
4. 코드 변경 없이 문서만 수정한다.
5. 링크, 목차, 경로가 실제 파일 구조와 맞는지 확인한다.

## Completion Rule

작업 완료 보고에는 다음 내용을 포함한다.

- 생성 또는 수정한 주요 파일.
- 실행한 검증.
- 기록한 실패 수정 로그 항목.
- 남은 위험이나 실행하지 못한 검증.
